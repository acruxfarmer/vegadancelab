# 6.3 — Staff Class Cancellation V1 verification record

Status: implementation and local verification complete on 2026-09-22. Hosted Development staff/member verification is pending deployment and authenticated sessions. This slice is not yet closed.

## Existing foundations and bounded refinement

The existing occurrence state already gates booking and promotion; member joining uses that same booking gate. The cancellation engine already restores the consumed unit under its original entitlement terms. The application store already locks the business aggregate and commits state and actor-scoped request receipts in one PostgreSQL transaction. Attendance and waitlist transition histories, member isolation, session recovery and audit projections are reused.

The missing capability was a reviewed occurrence-level orchestration. `cancel-class` calls the existing cancellation engine for each active reservation within that same transaction, classifies its restoration as early, and links the changes to one attributable occurrence event. It adds no parallel credit engine, schema, worker or service. Staff must supply a reason and the reviewed impact fingerprint. Changes to the occurrence, reservations or relevant debit lineage require a fresh preview. The authenticated staff projection and commit fingerprint both use the persisted occurrence, not derived availability fields.

All active bookings and waiting entries are cancelled once. Previously cancelled entries remain byte-for-byte unchanged. Waiting entries never move credits. Original debit units remain spent; restored units retain the original pass, source-unit/booking linkage, expiry and restrictions. Expired credits are restored without becoming usable or receiving an extension. Payment, notification and attendance fields are unchanged. Occurrence-initiated cancellations cannot be reclassified through the individual early/late correction form; separate reconciliation is required for that new case.

Any attendance history, nonzero attendance revision or recorded attendance state on any linked reservation blocks V1, including cleared attendance on an already-cancelled reservation. Invalid credit provenance or unsupported reservation states also block the entire operation. Staff-only history retains actor, time, reason, request, occurrence event and affected transitions. Member projections expose only their own safe reservation outcomes and public occurrence state, not staff reasons/actors or other members' affected records. Reports joins the existing lineage; it does not create parallel records.
